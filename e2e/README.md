# End-to-end browser checks (scratchpad)

**Status: these are scratchpad scripts, not a test suite.** They were
written while replacing the `tablesorter` plugin, to check the new
sortable tables on a real Corydalis server, in a real browser (and
later, to check a public-site build). They are kept for re-running by
hand when changing the tables, their templates, or what anonymous
visitors can see.
They are not ready for automated use (e.g. in CI):

- many checks depend on the exact sample library generated by
  `setup.sh` (folder and image counts, names, dates), and would break
  with any other library;
- they wait for the page with fixed short delays, rather than for
  specific conditions, so they can be flaky on slow machines;
- Playwright is not a dependency of the project (see below);
- they report results by printing `ok`/`FAIL` lines, not via a test
  runner.

The table logic itself is tested by `npm test` (see
`js/tablesort-logic.test.ts` and `js/tablesort.test.ts`), which is fast
and doesn't need a server or a browser.

**Experiment:** `make e2e` (`run.sh`) runs them all from scratch, and
the CI workflow runs it in its own job, to see how long it takes and
how reliable it is there. The limitations above still apply.

## Files

- `run.sh`: runs all the checks from scratch (see "Running all the
  checks" below);
- `smoke.cjs`: loads every page as a logged in user, and fails on an
  error status, a missing navigation bar or a browser console error;

- `setup.sh`: creates a work directory with a sample photo library (20
  folders, 120 small JPEG images with EXIF data), a `settings.yml` for
  it, and a test user;
- `lib.cjs`: shared configuration and the login helper;
- `pages.cjs`: records the state of every page with tables (rows,
  groups, filter controls) to a JSON report, plus screenshots; useful to
  compare before/after a change;
- `verify.cjs`: exercises the tables (sorting, shift-click, keyboard,
  groups, text/select/numeric filters, `aria-sort`), flagging (including
  the CSRF token, and a stale one), the plot pages and the viewer
  (navigation, flagging, random images), and fails on any browser
  console error;
- `shots.cjs`: takes screenshots of the tables, in a few states.
- `plots.cjs`: records the state of every chart on the plot pages
  (traces, bars and points, legend and axis labels, hover labels, the
  update menus, the width after resizing), the plotly version the
  browser received, and any console errors, to a JSON report, plus
  screenshots; with `--compare`, compares two such reports. Useful
  before/after a plotly update.
- `add-problem.sh`: adds a folder with a picture that has a problem (a
  truncated JPEG, for which exiftool warns "JPEG format error") to the
  library made by `setup.sh`;
- `public-site.cjs`: checks a public-site build (`make demo-release`):
  that anonymous visitors can browse the public pages, but don't see
  the pictures' problems, the storage paths or the tools' error output
  (in failed previews), that searches by problem and `/list/problems`
  are refused, that quick searches don't use problems, and that the
  settings, status and flagged images pages need a login; then, that a
  logged in user still sees all these.

## Requirements

- the frontend bundles (`npm run build`), built first, as they are
  embedded in the binaries;
- the Corydalis binaries (`corydalis` and `db-util`), built without the
  `dev` flag, which disables the executables:

      stack build --flag corydalis:-dev --copy-bins --local-bin-path BINDIR

- ImageMagick and exiftool, as for the application itself;
- Playwright with Chromium, installed outside the project, e.g. in a
  scratch directory:

      npm install playwright && npx playwright install chromium

  and then run the scripts with `NODE_PATH` pointing at that
  directory's `node_modules`, if needed.

## Running all the checks

    npm run build
    make e2e    # or: e2e/run.sh WORKDIR (default _run/e2e)

This builds the binaries (normal and public site, without
optimisation, in `.stack-e2e` and `.stack-e2e-public`), makes the two
libraries, starts a server for each (on ports 3001 and 3002, so as not to conflict with a development
server on 3000), runs
`smoke.cjs`, `verify.cjs`, `pages.cjs` and `plots.cjs` on the normal
one and `public-site.cjs` and `shots.cjs` on the public one, then stops
the servers. It exits with an error if any script failed. Set
`NODE_PATH` if Playwright is installed elsewhere, and `STACK_ARGS` for
extra stack options (e.g. `--ghc-build tinfo6`).

## Running the scripts by hand

From the root of the repository:

    e2e/setup.sh WORKDIR BINDIR
    BINDIR/corydalis WORKDIR/settings.yml &   # serves on port 3000
    export CORYDALIS_PASSWORD_FILE=WORKDIR/password
    node e2e/verify.cjs WORKDIR/verify
    node e2e/shots.cjs WORKDIR/shots
    node e2e/pages.cjs WORKDIR/pages
    node e2e/plots.cjs WORKDIR/plots

The server scans the library at startup; the scripts wait until the
folders show up. Set `CORYDALIS_URL` (default `http://localhost:3000`)
and `CORYDALIS_USER` (default `tester`) to use another server or user.

To check a public-site build, use a separate work directory, as the
other scripts expect the library exactly as `setup.sh` makes it:

    make demo-release                   # binaries in dist/
    e2e/setup.sh WORKDIR dist
    e2e/add-problem.sh WORKDIR
    dist/corydalis WORKDIR/settings.yml &
    export CORYDALIS_PASSWORD_FILE=WORKDIR/password
    node e2e/public-site.cjs WORKDIR

To compare the plots before and after a change (e.g. a plotly update),
record them with each version, then compare the reports, and the
screenshots (e.g. with ImageMagick):

    node e2e/plots.cjs WORKDIR/plots-before
    # update, rebuild the bundles (npm ci && npm run build), then the
    # binaries, and restart the server
    node e2e/plots.cjs WORKDIR/plots-after
    node e2e/plots.cjs --compare WORKDIR/plots-before WORKDIR/plots-after
    compare -metric AE WORKDIR/plots-before/curate.png \
      WORKDIR/plots-after/curate.png null:

The comparison exits with an error if any chart differs, or if either
run had console errors. Check that the reported plotly versions are the
expected ones: the browser can only get the new version once the
bundles are rebuilt.

Note that templates are compiled into the server binary, so changes to
them need a rebuild (and a restart). So do changes to the JavaScript and
CSS bundles (after `npm run build`) for a release build, which embeds
them; a development build serves them from `static/`, so for it a page
reload is enough.
